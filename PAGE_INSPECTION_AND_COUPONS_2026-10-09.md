# Rendered-page inspection and coupon evidence — 9 October 2026

## Implemented changes

`backend/page_inspection.py` reads the current rendered DOM locally. This replaces generic first-match coupon fields and Apply controls with label/ARIA associations and nearby structure. Multiple plausible fields/buttons, Pay/Book/Submit controls and hidden/disabled inputs are refused. Provider-specific adapters remain where their actual layout is better supported. Generic removal also refuses multiple plausible controls; unsupported layouts produce an error.

Only strictly labelled INR total/fee rows and coupon-control counts leave the page inspection. It excludes scripts, cookies, unrelated page text and personal form values. It recognises the visible EaseMyTrip rupee CSS icon, which ordinary text extraction misses. Conflicting totals, malformed money, per-person amounts and inspection-budget truncation cannot establish a payable total. The normal exact-itinerary, adult/cabin, selected-payment, unchanged-cart and stable-total checks still govern verification.

`inspect_page()` is an async context manager. Optional cropped monetary-row screenshots are held in memory, never written to a file or sent to Gemini/another service. Form elements and iframes are masked. Summary dictionaries, image buffers and browser handles are cleared/disposed in `finally`, including on failure or cancellation. This is application lifecycle cleanup, not a promise of forensic RAM erasure or control over browser/OS caches. The existing browser remains open for its booking session; normal session cleanup closes it. Screenshots are supporting diagnostic evidence; there is no OCR/vision-based price promotion. No OCR dependency, paid API or replacement browser engine was needed for this verified case.

A detected sign-in overlay aborts the run without force-clicking, logging in or trying further coupons behind it. Remaining codes stay untested; failed winner restoration never publishes a lower verified fare. The user must resolve the sign-in screen and reverify.

The public `probe_live.py` and `probe_navigation_20261009.py` tools no longer write full HTML, page text or screenshots, including on failures. The new `probe_memory_checkout.py` also avoids page dumps. Previously existing audit artifacts were preserved. Small structured navigation reports and scoped coupon facts remain available; they are distinct from downloaded page copies.

## Coupon track record

Two additive SQLite tables (`coupon_audit_runs` and `coupon_audit_trials`) record each run and each collected code's outcome immediately. Facts include directed route/date, flight, adult/cabin, payment category, review/payment stage, source/terms/expiry, time, displayed total and saving where observed. No passenger/card details or booking query tokens are stored. The database was backed up before initialising the additive schema.

Rejected coupons are distinguished from browser errors and missing acceptance evidence. Filtered, conditional, budget-limited and interrupted trials are retained. A run is only marked `checkout_verified` after the dispatcher repeats its exact booking/payment/cart checks and confirms the restored winning total. Runs interrupted before that point stay unverified. These facts do not enter fare training or update the legacy global coupon success score.

Unknown bank/card/account/add-on conditions are no longer automatically trialled as eligible at review. Plural Doctors/Nurses, Army/Government Personnel and existing-account restrictions are recognised; inclusive new-and-existing-user offers are not incorrectly restricted. Chance-based rewards are excluded from immediate payable savings. Newly displayed restrictions are assessed again after acceptance; an unknown condition cannot win merely because a review total dropped. Native terms take precedence over cached duplicates. Source-collection failure forces partial coverage. Every code is deduplicated; budget limits remain explicit, and no exhaustive global cheapest-coupon claim is made.

Results → Published coupons & bank offers → Coupon track record shows recent runs, individual outcomes and limitations. All collected published candidates are displayed, removing the old thirty-offer display cap. Choose the website using the Coupon website selector and refresh the track record after a run. The API returns the newest forty runs per website; older records remain in SQLite.

An uncapped eligible-code review run on CCU–PNQ, 18 February encountered an EMT sign-in overlay after account-related offers. It retained 38 trial records: four accepted reductions, three accepted without a saving, thirteen filtered, fourteen conditional, one inconclusive and three browser errors. Winner restoration failed behind the overlay; the run is explicitly failed, with no final payable price published and no fare learning. This prompted the additional account/profession checks and early overlay stop above. The subsequent fresh run tested all six eligible collected codes successfully: EASEFLY reduced ₹7,998 to ₹7,598, BOOKNOW to ₹7,778 and EMTQORUM to ₹7,798; EMTNCF, FREECAB and DELIGHT were accepted without an immediate fare reduction. Eighteen other codes stayed conditional and fourteen were filtered. The winning code was reapplied and its stable ₹7,598 review total confirmed. Coverage remains non-exhaustive because unresolved eligibility is not proof. The reader also captured ₹7,998 and one cropped in-memory image, then cleared both. Four durable runs now hold 152 trial records; the failed run remains alongside the successful review runs.

## Validation and remaining limits

The final full isolated suite passed **374 tests** (136.36 seconds). Frontend production build and ESLint both passed; the diagnostics skill passed its bundled validator. The legacy research-model suite still emits one XGBoost pickle-version warning; it does not enable that legacy model for live booking decisions. Tests use disposable local fixtures; none are production seeds. Meaningful cases cover ambiguity, accidental payment buttons, hidden/malformed/conflicting money, cropped-buffer cleanup, source failures, interrupted runs, newly exposed conditions and no global learning from a review trial.

This work does not make refused provider pages accessible, expose fees that the provider has not yet displayed, prove issuer/gateway charges or calibrate a cold-start forecast. Coupon applicability can change with fare, account, payment, quota and time. Reverification remains necessary. The forecast data/history limitations in the prior audit remain in force.

The implementation follows official [Playwright page evaluation](https://playwright.dev/python/docs/evaluating), [in-memory screenshot buffers](https://playwright.dev/python/docs/screenshots) and [masked element screenshots](https://playwright.dev/python/docs/api/class-locator). Keeping Playwright and SQLite avoided another agent runtime, paid model, extra credentials and a second source of truth for money.
